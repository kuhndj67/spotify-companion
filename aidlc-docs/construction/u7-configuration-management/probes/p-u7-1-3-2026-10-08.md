## P-U7-1 — Does a four-value file with a placeholder token work on the first poll? ✅ YES

Input: `{ clientId, clientSecret, redirectUri, refreshToken, accessToken: "placeholder", expiresAt: 0 }` — exactly
BR-56.4's shape.

| Observation | Result |
|---|---|
| MCP server log on the first poll | `Access token expired or missing expiration time, refreshing...` → `Access token refreshed successfully` |
| `accessToken` after | a real token (392 characters), no longer `placeholder` |
| `expiresAt` after | in the future — **59.8 minutes** |
| `refreshToken` after | **unchanged** (byte-identical to the live one) |
| Keys after | exactly the six written — nothing added or dropped |
| Poll result | a genuine `Nothing is currently playing on Spotify` |

⚠️ **Why "nothing playing" is evidence and not absence**: `/me/player` needs a **user** token. Had the server
fallen back to client-credentials (F2), the call would have **failed** with an error text, not returned *nothing
playing*. The control for this is P-U7-3, which shows what a failure looks like on the same path.

✅ **BR-56.4 is confirmed. Code Generation Q1's fallback (the app refreshing once itself) is NOT needed.**
✅ **F3 re-confirmed**: refresh with a refresh token that the live deployment is also using, and the token is
neither rotated in the file nor (per the live deployment's continued health) invalidated.

## P-U7-2 — Does closing the MCP client end the child process? ✅ YES — after ~2 s

Script run inside the copy's container, spawning the server exactly as `SpotifyMcpClient` does
(`StdioClientTransport`, `process.execPath`, `/opt/spotify-mcp/build/index.js`), counting processes via `/proc`.

| | |
|---|---|
| MCP processes before / during / after | **1 / 2 / 1** (the app's own process untouched) |
| `getNowPlaying` through the probe's client | `nothing playing`, `isError: false` |
| Child exited after `close()` | ✅ after **2004 ms** |

⚠️ **Design consequence — 2 s, not instant.** `close()` returns before the child is gone; the SDK appears to wait
~2 s before forcing it. P-49's *"close and **await the exit**"* is therefore load-bearing: a write issued straight
after `close()` would land while the old server could still be inside a refresh. `SpotifyMcpClient.close()` must
resolve on the **exit**, with a bound (≥ 5 s) and an error if exceeded.

| Variant | Raw text reaching the app | Snapshot | M4 |
|---|---|---|---|
| Corrupted refresh token (realistic: wrong credentials entered) | `Error getting current track: Failed to refresh access token. Please run "npm run auth" to re-authenticate.` | `playing: true`, every field null, `isPlaying: false` → **PAUSED** | idle share **0** (counted as **playing**); MCP errors **0** |
| Placeholder example config (U6's copy) | `Error getting current track: Failed to get access token.` | same | same |

✅ **F5 confirmed live, exactly as read from source** — and the corrected direction stands: a credential failure
is counted as a **playing** poll, not idle.
✅ BR-58.1's `^Error [a-z]+ing\b.*:` matches both. Negative controls: `Nothing is currently playing on Spotify` →
no match; a now-playing block whose track title begins *"Error handling:"* → no match (the pattern is anchored at
the start of the text, and a now-playing block starts with `# Currently`).

⚠️ Both texts are added to Step 4's fixtures verbatim — the real strings, not invented ones (the *fixtures confirm
the model* lesson).
